# R3.2b — Cairn worker activity capture (observability only)

Implements Part B of `R4-LIVE-TRACE-SPEC.md`: dispatcher workers now stream their
`pi --mode json` events into `project_activity`, and the server exposes an active/recent
worker-runs API with each run's transcript. No worker steering, approvals, UI, Artex fork,
`dispatch.yaml`, frozen B=44 job/`f42.bin`, or live service was touched.

## 1. Streaming stdout capture

`LocalProcess`/`ManagedProcess` accept an optional `on_stdout_line` callback:

* stdout/stderr are read as **bytes**; each stream has its own
  `codecs.getincrementaldecoder("utf-8")(errors="replace")`, so a multibyte character split
  across pipe reads is reassembled (no U+FFFD corruption);
* complete LF-framed lines are delivered **while the process is running**, without the LF
  (a trailing `\r` is stripped);
* a final line without LF is delivered at EOF;
* the final `ProcessResult.stdout/stderr` is still the concatenation of the whole decoded
  stream (same text as before for valid UTF-8; split characters are now correct instead of
  replaced), including the old `text=True` universal-newline translation (CRLF/CR → LF);
* callback exceptions are logged and never kill the reader thread.

Container path is implemented (`ManagedProcess` + `Docker exec` demux chunks) and
unit-tested with a fake Docker stream; it was **not** exercised against a real Docker daemon
in this build (see Gaps).

## 2. Pi event parser and recorder

`PiWorkerEventParser` maps only events pi actually emitted:

| pi event | persisted activity |
| --- | --- |
| `message_update.thinking_start/delta/end` | `worker_thinking` (`streaming` → `done`), throttled ~2/s live updates |
| `tool_execution_start` | `tool_call` (`running`, name + input JSON) and an empty `tool_result` (`running`) |
| `tool_execution_update` | updates the matching `tool_result` description with partial output |
| `tool_execution_end` | `tool_result` (`done`/`error`, output, `is_error`, `duration_ms`), closes `tool_call` |
| `message_start/update/end` (assistant text) | `worker_message` (`streaming` → `done`, final text, model, usage, stop reason) |
| `extension_error`, `message_update.error`, `auto_retry_end.finalError` | `worker_error` |
| non-JSON stdout line | `worker_output` (verbatim, bounded) |
| `session`, `agent_start`, `turn_start`, `turn_end`, `agent_end`, unknown events | no transcript row; `worker_run` covers lifecycle |

No synthetic events: system/user/toolResult messages and toolcall deltas are not duplicated;
tool results are paired by `toolCallId`; unknown event types are ignored rather than
invented.

`WorkerActivityRecorder` posts start/transcript/finish rows through the existing activity
API (`CairnClient`) on a **bounded queue + single writer thread**, so a slow server can never
block the stdout drain thread and stall the worker. All recorder/HTTP failures are logged and
never fail the task. On finish it flushes accumulated partials (a stopped turn keeps the text
pi streamed), then calls the idempotent close endpoint, which terminalises every open child
row. Normal success, failure, timeout, cancellation and `finally` paths all close the run.

Run rows carry: `project_id`, `run_id`, `actor` (worker), `task`
(`bootstrap`/`reason`/`explore`/`*_conclude`), `intent_id`, `intent_description`, server
`created_at`, dispatcher `started_at`/`finished_at`, duration, session, return code,
timeout/cancel flags, and bounded raw event JSON (4 KB; descriptions 20 KB).

Non-pi workers (`claudecode`, `codex`, `mock`) still get `worker_run` lifecycle rows, but no
transcript because their stdout is not JSONL.

## 3. API contract (for the R3.2a UI builder)

### `GET /projects/{project_id}/workers`

Query: `worker`, `run_id`, `active_only` (default false), `include_transcript` (default
true), `limit` runs (default 20), `transcript_limit` steps (default 200), `stale_after_seconds`
(default 900).

```json
{
  "project_id": "proj_006",
  "generated_at": "2026-10-30T01:31:14Z",
  "active_count": 0,
  "items": [{
    "run_id": "58b0683521a141c4a4043228e77c6ca3",
    "project_id": "proj_006",
    "worker": "pi-http",
    "task": "explore",
    "intent_id": "i001",
    "intent_description": "run the tool trace smoke",
    "status": "success",
    "active": false,
    "stale": false,
    "started_at": "2026-10-30T01:31:14Z",
    "finished_at": "2026-10-30T01:31:14Z",
    "last_event_at": "2026-10-30T01:31:14Z",
    "duration_ms": 120,
    "error": null,
    "session": "sess-1",
    "transcript_truncated": false,
    "counts": {"activities": 4, "thinking": 1, "tool_calls": 1,
               "tool_results": 1, "messages": 1, "errors": 0},
    "transcript": [
      {"kind": "worker_thinking", "status": "done", "description": "plan",
       "metadata": {"run_id": "58b0…", "content_index": 0, "activity_id": 9}, "...": "..."},
      {"kind": "tool_call", "status": "done",
       "description": "{\"command\": \"echo CAIRN_WORKER_TRACE_OK\"}",
       "metadata": {"tool_name": "bash", "tool_call_id": "call_1",
                    "tool_input": "{\"command\": \"echo CAIRN_WORKER_TRACE_OK\"}"}, "...": "..."},
      {"kind": "tool_result", "status": "done", "description": "CAIRN_WORKER_TRACE_OK\n",
       "metadata": {"tool_name": "bash", "tool_call_id": "call_1",
                    "tool_output": "CAIRN_WORKER_TRACE_OK\n", "is_error": false,
                    "duration_ms": 4}, "...": "..."},
      {"kind": "worker_message", "status": "done", "description": "{\"accepted\":true,...}",
       "metadata": {"stop_reason": "stop", "usage": {"...": "..."}}, "...": "..."}
    ]
  }]
}
```

Semantics the UI can rely on:

* `items` are sorted newest first; `transcript` is in emission order (`project_activity.id`).
  Do not re-sort the transcript by `created_at` (it has second resolution).
* `status` is the latest `worker_run` row: `running`, `success`, `failed`, `timeout`,
  `cancelled` (also accepted by the close API: `error`, `stopped`).
* `active` = open run and not stale. A run whose dispatcher disappeared stays `status:
  "running"` but gets `stale: true` and `active: false` after `stale_after_seconds` — the
  server never rewrites evidence.
* Pair `tool_call`/`tool_result` by `metadata.tool_call_id`, not adjacency. Render Bash from
  `metadata.tool_input`, not raw JSON. A `tool_result` row is created empty with
  `status: "running"` when the tool starts, then its `description` fills with output as pi
  emits it; hide the empty card if you prefer, but keep the pairing. `metadata.is_error`
  marks a failed tool and `metadata.error` carries its error text.
* `worker_thinking` and `worker_message` rows are created with `status: "streaming"` and an
  initially empty/short `description`; their `description` grows (throttled) and is
  authoritative at `done`. `worker_output` is non-JSON stdout, shown verbatim if desired.
* Use `worker_run.runs/{run_id}` for a focused run; poll either endpoint every ~1 s while
  `active` (or while any run's status is `running`). `transcript_limit` returns the newest N
  steps, still in ascending order. For a multi-run view, poll the list with
  `include_transcript=false` and fetch only the selected run's detail; for a single worker
  lane, one `GET /workers` call with a small `limit` is enough.
* `counts` is computed over the whole run, even when the transcript is truncated.

### `GET /projects/{project_id}/workers/runs/{run_id}`

Same object, plus optional `include_transcript`, `transcript_limit`, `stale_after_seconds`.
`404` for an unknown run.

### `PATCH /projects/{project_id}/workers/activity/{activity_id}`

Dispatcher-only live updates for a transcript row (a row with a `run_id` and a worker kind):

```json
{"status": "done", "description": "the whole thought", "metadata": {"tokens": 7}}
```

At least one field is required (`400` otherwise); non-transcript rows are `409`; missing
rows are `404`. `metadata` is merged (the server keeps `run_id`). Returns the updated
`ProjectActivityItem`.

### `POST /projects/{project_id}/workers/runs/{run_id}/close`

```json
{"status": "cancelled", "error": "project stopped", "metadata": {"duration_ms": 1234}}
```

Idempotent: closes every `running`/`streaming` row belonging to the run, and appends exactly
one terminal `worker_run` row (a second call returns the existing terminal row). Body may be
omitted (defaults to `success`). Returns the `WorkerRunItem` summary with an empty
transcript (fetch the run detail for steps) so the dispatcher's close request never
serializes a large transcript.

### `GET /projects/{project_id}/activity`

Unchanged shape and cursor. Worker kinds are included by default and can be selected with
`kinds=worker_run,worker_thinking,tool_call,tool_result,worker_message,worker_error,worker_output`.
Each item now also carries top-level `run_id`; worker items put worker/task/intent/run fields
in `metadata`.

Note: `kinds=tool` still means **chat** tool calls (the existing mapping), while
`kinds=tool_call` means **worker** tool calls. Use the dedicated `/workers` endpoint if you
want the grouped view.

## 6. Gaps / explicitly not done

1. **Container path is not exercised against a real Docker daemon.** `ManagedProcess` gets
   the same decoder/framing/callback and is unit-tested with a fake demux stream; the live
   deployment here is `runtime.execution: local`. No `docker` run was attempted to avoid
   touching unrelated containers.
2. **Non-pi workers have lifecycle rows only.** Claude Code/Codex/mock stdout is not JSONL;
   their transcript is not guessed. They still appear in `/workers` with `counts=0`.
3. **Dispatcher SIGKILL/OOM/hard shutdown can leave an open run.** Normal
   cancel/timeout/exception paths close in `finally`; a hard kill cannot. Such runs are
   surfaced as `stale:true, active:false` after 900 s, but the server does not rewrite the
   rows. A future reconciler could close them with an explicit "dispatcher died" status.
4. **Live updates are throttled** (~2/s per stream). The first thinking delta updates
   immediately; later deltas and tool partial output are coalesced to keep HTTP/SQLite load
   low. Final `*_end` events are authoritative.
5. **Bounded, not lossless.** Queue overflow drops events (counted in
   `metadata.dropped_events`); descriptions are clipped at 20 KB, raw events at 4 KB. A
   permanently stalled writer leaves the run open for stale detection rather than posting a
   finish row out of order.
6. **No auth on the new endpoints**, same as the existing API. They are intended for the
   local UI/dispatcher, not exposed publicly.
7. **Worker steering/approvals remain phase 3**, per the spec. This build is observability
   only.
8. **UI untouched.** R3.2a consumes the contract above; the existing Activity tab keeps
   working because `/activity` is backward compatible.
9. **No retention/pruning.** Worker transcript rows live in `project_activity` and grow with
   every run (bounded per row, not per project). Deleting a project cascades them away; a
   long-lived project needs an explicit retention policy later.

## 7. Live restart (NOT run)

The live server (`:8000`, PID 264368) and dispatcher (PID 7912) kept running the pre-change
code during this build. The live DB still has the old `project_activity` schema (no
`run_id`); the migration applies only when the new server starts. Verified after the build:
the live DB's `PRAGMA table_info(project_activity)` still has no `run_id`, and both live
PIDs were unchanged; the temp `:8019` server was stopped.

Restart the **server first** (it adds `run_id` and serves the worker endpoints), then the
dispatcher (it loads the streaming recorder):

```bash
systemctl --user restart cairn-server.service
# wait until the API answers, then:
systemctl --user restart cairn-dispatcher.service
```

Migrations are idempotent (`_ensure_worker_activity_columns`). Dispatcher restart only
affects workers started afterwards; in-flight workers finish under the old code and are not
transcribed. No live DB migration, service restart, or `dispatch.yaml` change was performed
as part of this build.
